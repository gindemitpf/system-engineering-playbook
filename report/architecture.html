Архитектура системы

4.1. Общий архитектурный подход

Система строится как модульная микросервисная информационная система с выделенными функциональными компонентами: управление резюме, интеллектуальный анализ (AI Analysis), рекомендации (Matching) и аудит. Анализ резюме является ресурсоёмкой и длительной операцией, поэтому система использует асинхронную модель обработки через очередь сообщений (Message Broker) для обеспечения отзывчивости UI.

Критичные данные (профили кандидатов, результаты анализа) хранятся в PostgreSQL с соблюдением требований безопасности (шифрование, аудит доступа). Использование внешних AI-моделей (LLM) инкапсулировано в отдельном сервисе, что позволяет гибко менять провайдеров или модели без переписывания бизнес-логики.

4.2. C4 Context

Контекстная диаграмма показывает систему как центр автоматизации найма:

  • Кандидаты взаимодействуют с порталом для загрузки резюме;
  • HR и руководители работают с Web UI для управления вакансиями и анализа кандидатов;
  • Система интегрируется с внешними AI-провайдерами для NLP-задач;
  • SSO используется для аутентификации сотрудников;
  • Система мониторинга собирает метрики и логи;
  • Корпоративная ATS/CRM интегрируется для обмена данными о закрытых вакансиях.

4.5. Механизм защиты и идемпотентности

  1. Idempotency-Key: При загрузке резюме вычисляется хэш файла; повторная загрузка того же файла не запускает повторный AI-анализ.
  2. PII Masking: Перед отправкой данных в AI Model API, персональные данные (ФИО, контакты) удаляются или заменяются токенами.
  3. Transactional Integrity: Запись результатов анализа в PostgreSQL выполняется внутри транзакции.

4.6. ADR

ADR-1. Асинхронная обработка резюме через Message Broker

Контекст: AI-анализ занимает от 5 до 30 секунд. Решение: Использовать брокер сообщений для постановки задач анализа в очередь. Trade-off: Повышается сложность инфраструктуры, но пользовательский интерфейс остается отзывчивым (получает статус «в обработке» мгновенно).

ADR-2. Использование внешнего AI API с прослойкой обезличивания

Контекст: необходимо анализировать текст, содержащий ПДн. Решение: Анализ выполняется через API (например, OpenAI), но сервис перед отправкой запроса фильтрует PII. Trade-off: Усложнение сервиса анализа, но минимизация рисков компрометации персональных данных.

ADR-3. Разделение сервисов анализа и рекомендаций

Контекст: логика парсинга (NLP) и логика ранжирования (бизнес-правила) требуют разных инструментов. Решение: AI Analysis Service только извлекает сущности, Recommendation Service строит рейтинг. Trade-off: Упрощается независимое масштабирование (анализ можно масштабировать при пиках нагрузки на загрузку резюме).

ADR-4. Использование событийной модели для статусов

Контекст: система должна реагировать на завершение анализа мгновенно. Решение: Использовать паттерн Event-Driven для публикации события ResumeAnalyzed. Trade-off: Повышение связанности через контракты событий, но значительное ускорение реакции системы.
