О работе: AI-сервис первичного отбора кандидатов

Назначение системы: автоматизация первичного анализа резюме, ранжирование кандидатов на основе соответствия требованиям вакансии и генерация персонализированных вопросов для собеседования.

Система (SoI): интеллектуальная система первичного отбора кандидатов, включающая Web UI, сервисы обработки резюме и AI-анализа, а также модуль рекомендаций.

Основные сценарии: загрузка резюме, интеллектуальный анализ навыков, сопоставление (matching), ранжирование и генерация вопросов.

Контекст и границы SoI

1.1. Цель системы

Целью системы является автоматизация первичного отбора кандидатов, повышение объективности оценки навыков и снижение рутинной нагрузки на HR-департамент за счёт интеллектуального анализа резюме, автоматизированного сопоставления с требованиями вакансий и генерации уточняющих вопросов для собеседований.

Система должна обеспечивать качественную обработку неструктурированных данных резюме, предотвращать предвзятость при первичном скрининге, учитывать специфику вакансий и предоставлять HR-специалистам актуальные данные для принятия решений о приглашении на интервью.

1.4. Границы системы

Внутри SoI

В состав системы входят:

  • веб-интерфейс (Web UI) для HR и руководителей;
  • сервис обработки резюме (Resume Service);
  • сервис анализа и сопоставления (AI Analysis & Recommendation Service);
  • API Gateway / Backend API;
  • основная база данных (PostgreSQL);
  • брокер сообщений (Message Broker) для асинхронной обработки;
  • модуль генерации вопросов (LLM Integration Client);
  • система журналирования и аудита.

Вне SoI

За пределами системы находятся:

  • корпоративный SSO / IdP;
  • внешние AI-провайдеры (OpenAI, Anthropic, и др.);
  • внешние системы хранения файлов (AWS S3 и аналоги);
  • существующие корпоративные ATS/CRM-системы;
  • внешние средства мониторинга;
  • фактические собеседования и итоговые решения HR;
  • политика компании по критериям найма.

1.6. Допущения и ограничения

  1. Система ориентирована на работу с резюме в форматах PDF и DOCX.
  2. AI-анализ является вспомогательным инструментом; финальное решение всегда принимает человек (Human-in-the-loop).
  3. Система использует асинхронную обработку для тяжелых AI-операций.
  4. Персональные данные кандидатов (PII) должны быть обезличены перед отправкой во внешние AI API.
  5. При недоступности AI API система должна накапливать задачи в очереди (Retry policy).
  6. Безопасность данных обеспечивается шифрованием "at rest" и "in transit".
  7. Доступ к системе для HR и руководителей разграничен по ролям (RBAC).
  8. Администратор обеспечивает мониторинг стоимости и эффективности использования внешних AI-моделей.

2.2. Сценарий UC-01. Загрузка и первичная обработка резюме

Цель: автоматическое извлечение данных из резюме кандидата для дальнейшего анализа.

Участники: кандидат, Web UI, Resume Service, Message Broker, AI Analysis Service, PostgreSQL.

Основной поток:

  1. Кандидат загружает файл резюме (PDF/DOCX) через Web UI.
  2. Resume Service сохраняет файл в облачное хранилище и публикует событие ResumeUploaded в Message Broker.
  3. AI Analysis Service подписывается на событие, скачивает файл и отправляет текст резюме в LLM для парсинга.
  4. AI Analysis Service сохраняет структурированные данные (навыки, опыт, образование) в PostgreSQL.
  5. Система обновляет статус кандидата на «Готов к анализу».

Режимы деградации:

  • При недоступности AI API задача встает в очередь (Retry policy) до восстановления сервиса.

2.3. Сценарий UC-02. Сопоставление с вакансией (Matching)

Цель: ранжирование кандидатов на основе их соответствия требованиям конкретной вакансии.

Участники: HR, Web UI, Recommendation Service, PostgreSQL.

Основной поток:

  1. HR привязывает конкретную вакансию к профилю кандидата.
  2. Recommendation Service извлекает профиль кандидата и требования вакансии.
  3. Система производит семантическое сопоставление навыков (Match Score) и формирует рейтинг (0-100%).
  4. HR получает список кандидатов, отсортированный по уровню соответствия.

Исключения:

  • Недостаточно данных в резюме для объективной оценки.

Результат: HR видит список кандидатов с обоснованием рейтинга.

2.4. Сценарий UC-03. Генерация вопросов для интервью

Цель: подготовка персонализированного скрипта интервью для HR на основе выявленных "пробелов" в навыках.

Участники: HR, Web UI, Recommendation Service, LLM, PostgreSQL.

Основной поток:

  1. HR выбирает кандидата из списка для приглашения на собеседование.
  2. Recommendation Service выявляет области, где квалификация кандидата ниже требований вакансии.
  3. Система отправляет запрос в LLM для генерации 3-5 уточняющих вопросов.
  4. Скрипт вопросов сохраняется в карточке кандидата.

Результат: HR получает готовый список вопросов, помогающих закрыть сомнения по кандидату.

2.5. Сценарий UC-04. Работа при недоступности AI-модели

Цель: сохранение работоспособности системы (загрузка и хранение данных) при сбое внешнего AI API.

Участники: Resume Service, Message Broker, AI Analysis Service, AI Model API.

Основной поток:

  1. Резюме загружается и сохраняется в БД.
  2. Событие обработки отправляется в Message Broker.
  3. AI Analysis Service при попытке обращения к AI Model API получает ошибку 5xx.
  4. Система переводит задачу в статус pending_retry и выполняет отложенную отправку согласно политике (exponential backoff).

Результат: данные кандидата не теряются; анализ выполняется автоматически сразу после восстановления доступа к AI API.

2.6. Сценарий UC-05. Управление доступом и аудит

Цель: обеспечение безопасности данных и прозрачности работы AI.

Участники: администратор, HR, PostgreSQL.

Основной поток:

  1. HR или руководитель авторизуются через корпоративный SSO.
  2. Система проверяет права (RBAC) на просмотр конкретной вакансии.
  3. Любое изменение рейтинга или просмотр ПДн фиксируется в Audit Log.

Результат: исключение несанкционированного доступа к резюме и прозрачная история работы с кандидатами.

Архитектура системы

4.1. Общий архитектурный подход

Система строится как модульная микросервисная информационная система с выделенными функциональными компонентами: управление резюме, интеллектуальный анализ (AI Analysis), рекомендации (Matching) и аудит. Анализ резюме является ресурсоёмкой и длительной операцией, поэтому система использует асинхронную модель обработки через очередь сообщений (Message Broker) для обеспечения отзывчивости UI.

Критичные данные (профили кандидатов, результаты анализа) хранятся в PostgreSQL с соблюдением требований безопасности (шифрование, аудит доступа). Использование внешних AI-моделей (LLM) инкапсулировано в отдельном сервисе, что позволяет гибко менять провайдеров или модели без переписывания бизнес-логики.

4.2. C4 Context

Контекстная диаграмма показывает систему как центр автоматизации найма:

  • Кандидаты взаимодействуют с порталом для загрузки резюме;
  • HR и руководители работают с Web UI для управления вакансиями и анализа кандидатов;
  • Система интегрируется с внешними AI-провайдерами для NLP-задач;
  • SSO используется для аутентификации сотрудников;
  • Система мониторинга собирает метрики и логи;
  • Корпоративная ATS/CRM интегрируется для обмена данными о закрытых вакансиях.

4.5. Механизм защиты и идемпотентности

  1. Idempotency-Key: При загрузке резюме вычисляется хэш файла; повторная загрузка того же файла не запускает повторный AI-анализ.
  2. PII Masking: Перед отправкой данных в AI Model API, персональные данные (ФИО, контакты) удаляются или заменяются токенами.
  3. Transactional Integrity: Запись результатов анализа в PostgreSQL выполняется внутри транзакции.
CREATE UNIQUE INDEX ux_resume_hash 
ON resumes (hash) 
WHERE status IN ('processed', 'processing');

4.6. ADR

ADR-1. Асинхронная обработка резюме через Message Broker

Контекст: AI-анализ занимает от 5 до 30 секунд. Решение: Использовать брокер сообщений для постановки задач анализа в очередь. Trade-off: Повышается сложность инфраструктуры, но пользовательский интерфейс остается отзывчивым (получает статус «в обработке» мгновенно).

ADR-2. Использование внешнего AI API с прослойкой обезличивания

Контекст: необходимо анализировать текст, содержащий ПДн. Решение: Анализ выполняется через API (например, OpenAI), но сервис перед отправкой запроса фильтрует PII. Trade-off: Усложнение сервиса анализа, но минимизация рисков компрометации персональных данных.

ADR-3. Разделение сервисов анализа и рекомендаций

Контекст: логика парсинга (NLP) и логика ранжирования (бизнес-правила) требуют разных инструментов. Решение: AI Analysis Service только извлекает сущности, Recommendation Service строит рейтинг. Trade-off: Упрощается независимое масштабирование (анализ можно масштабировать при пиках нагрузки на загрузку резюме).

ADR-4. Использование событийной модели для статусов

Контекст: система должна реагировать на завершение анализа мгновенно. Решение: Использовать паттерн Event-Driven для публикации события ResumeAnalyzed. Trade-off: Повышение связанности через контракты событий, но значительное ускорение реакции системы.

7.3. Тест-кейсы

TC-01. Успешная загрузка резюме

Цель: проверить, что кандидат может загрузить файл, и система переходит в статус processing. Шаги: выбрать файл (PDF), нажать «Загрузить», проверить статус в API. Покрываемые требования: SR-SH-1, SR-SH-2.

TC-02. Корректный анализ навыков (AI)

Цель: проверить извлечение навыков из текста. Данные: эталонное резюме Java-разработчика. Ожидаемый результат: система извлекла «Java», «Spring», «SQL». Покрываемые требования: SR-SYS-2, SR-SYS-6.

TC-03. Проверка обезличивания (PII Masking)

Цель: убедиться, что ФИО и телефон не попадают в AI-модель. Метод: инспекция логов запросов к AI-провайдеру. Ожидаемый результат: данные маскируются на [MASKED]. Покрываемые требования: SR-SH-11, NFR-7.

TC-04. Ранжирование кандидатов (Match Score)

Цель: проверить адекватность рейтинга. Данные: два резюме (одно релевантное, другое нет). Ожидаемый результат: релевантное резюме имеет Match Score > 80%, нерелевантное < 30%. Покрываемые требования: SR-SH-5, SR-SYS-3.

TC-05. Генерация вопросов для интервью

Цель: проверка наличия вопросов в ответе API. Шаги: вызвать метод /interview-questions. Ожидаемый результат: возвращено 3-5 вопросов, связанных с профилем вакансии. Покрываемые требования: SR-SH-6, SR-SYS-4.

TC-08. Авторизация и доступ (RBAC)

Цель: проверить разделение прав HR и Администратора. Шаги: попытка HR изменить системные настройки. Ожидаемый результат: 403 Forbidden. Покрываемые требования: SR-SH-9, SR-SYS-9, NFR-8.

TC-10. Шифрование данных

Цель: проверить, что резюме в БД не хранится в открытом виде. Метод: инспекция БД (скриншот хранилища). Покрываемые требования: SR-SYS-13.

TC-13. Обработка ошибок при недоступности AI

Цель: проверить retry-логику. Шаги: имитация 5xx ошибки от OpenAI. Ожидаемый результат: задача перешла в очередь повторов, в логах — Retry attempt 1/3. Покрываемые требования: SR-SYS-11, SR-SYS-12.

TC-14. Нагрузочное тестирование

Цель: проверка времени обработки резюме под нагрузкой. Шаги: подача 50 резюме одновременно. Ожидаемый результат: время обработки p95 < 30 секунд. Покрываемые требования: NFR-1, NFR-4.
