

# CONOPS / OPSCON

## 2.1. Роли

| Роль | Описание деятельности | Основные операции |
| --- | --- | --- |
| Кандидат | Взаимодействует с системой для участия в отборе | Загрузка резюме, просмотр статуса, ответы на вопросы |
| HR | Управляет процессом найма и потоком кандидатов | Создание вакансий, анализ отчетов, приглашение на интервью |
| Руководитель отдела | Формирует требования и принимает решение о найме | Определение критериев отбора, выбор финалистов |
| Администратор | Обеспечивает эксплуатацию системы | Настройка доступа, контроль использования AI-лимитов |

## 2.2. Сценарий UC-01. Загрузка и первичная обработка резюме

**Цель:** автоматическое извлечение данных из резюме кандидата для дальнейшего анализа.

**Участники:** кандидат, Web UI, Resume Service, Message Broker, AI Analysis Service, PostgreSQL.

**Основной поток:**

1. Кандидат загружает файл резюме (PDF/DOCX) через Web UI.
2. Resume Service сохраняет файл в облачное хранилище и публикует событие `ResumeUploaded` в Message Broker.
3. AI Analysis Service подписывается на событие, скачивает файл и отправляет текст резюме в LLM для парсинга.
4. AI Analysis Service сохраняет структурированные данные (навыки, опыт, образование) в PostgreSQL.
5. Система обновляет статус кандидата на «Готов к анализу».

**Режимы деградации:**

* При недоступности AI API задача встает в очередь (Retry policy) до восстановления сервиса.

## 2.3. Сценарий UC-02. Сопоставление с вакансией (Matching)

**Цель:** ранжирование кандидатов на основе их соответствия требованиям конкретной вакансии.

**Участники:** HR, Web UI, Recommendation Service, PostgreSQL.

**Основной поток:**

1. HR привязывает конкретную вакансию к профилю кандидата.
2. Recommendation Service извлекает профиль кандидата и требования вакансии.
3. Система производит семантическое сопоставление навыков (Match Score) и формирует рейтинг (0-100%).
4. HR получает список кандидатов, отсортированный по уровню соответствия.

**Исключения:**

* Недостаточно данных в резюме для объективной оценки.

**Результат:** HR видит список кандидатов с обоснованием рейтинга.

## 2.4. Сценарий UC-03. Генерация вопросов для интервью

**Цель:** подготовка персонализированного скрипта интервью для HR на основе выявленных "пробелов" в навыках.

**Участники:** HR, Web UI, Recommendation Service, LLM, PostgreSQL.

**Основной поток:**

1. HR выбирает кандидата из списка для приглашения на собеседование.
2. Recommendation Service выявляет области, где квалификация кандидата ниже требований вакансии.
3. Система отправляет запрос в LLM для генерации 3-5 уточняющих вопросов.
4. Скрипт вопросов сохраняется в карточке кандидата.

**Результат:** HR получает готовый список вопросов, помогающих закрыть сомнения по кандидату.

## 2.5. Сценарий UC-04. Работа при недоступности AI-модели

**Цель:** сохранение работоспособности системы (загрузка и хранение данных) при сбое внешнего AI API.

**Участники:** Resume Service, Message Broker, AI Analysis Service, AI Model API.

**Основной поток:**

1. Резюме загружается и сохраняется в БД.
2. Событие обработки отправляется в Message Broker.
3. AI Analysis Service при попытке обращения к AI Model API получает ошибку 5xx.
4. Система переводит задачу в статус `pending_retry` и выполняет отложенную отправку согласно политике (exponential backoff).

**Результат:** данные кандидата не теряются; анализ выполняется автоматически сразу после восстановления доступа к AI API.

## 2.6. Сценарий UC-05. Управление доступом и аудит

**Цель:** обеспечение безопасности данных и прозрачности работы AI.

**Участники:** администратор, HR, PostgreSQL.

**Основной поток:**

1. HR или руководитель авторизуются через корпоративный SSO.
2. Система проверяет права (RBAC) на просмотр конкретной вакансии.
3. Любое изменение рейтинга или просмотр ПДн фиксируется в Audit Log.

**Результат:** исключение несанкционированного доступа к резюме и прозрачная история работы с кандидатами.
